# metaharness GitHub Action

`metaharness Agent` runs Claude, Cursor, Codex, or the mock provider through the
same harness API used by the SDK and CLI. It records normal run artifacts under
`.harness/runs/<run-id>/` and exposes the run id, final status, final message,
patch, ledger, and handoff paths as step outputs.

## Inputs

- `provider`: required provider id: `claude`, `cursor`, `codex`, or `mock`.
- `task`: inline prompt text. Use either `task` or `task-file`, not both; the
  selected prompt source must contain non-whitespace text.
- `task-file`: path to a prompt file in the checked-out workspace. The path is
  resolved relative to the action working directory; missing or unreadable files
  fail before a provider run starts.
- `verify`: one or more verification commands, one command per line. Commands
  are parsed into argv arrays by metaharness and are not run through shell string
  interpolation.
- `policy-file`: policy file path. Defaults to `metaharness.policy.yaml`. If
  omitted and the default file is absent, provider defaults apply; if an
  explicit path is provided, it must exist.
- `config-file`: harness config path. Defaults to `metaharness.config.ts`. If
  omitted and the default file is absent, the action uses a provider default
  config; if an explicit path is provided, it must exist. Existing config files
  are imported as plain ESM and validated against the metaharness config schema.
  Avoid runtime imports unless those packages are installed in the checked-out
  workspace.
- `fallback-provider`: optional provider to receive a ledger handoff if the
  initial run completes with a non-success status.
- `open-pull-request`: when true, stages workspace changes outside `.harness`,
  commits them on a `metaharness/<run-id>` branch, pushes the branch, and opens a
  pull request.
- `allow-pull-request-target`: defaults to `false`. Set it to `true` only in
  workflows that perform explicit trust checks before invoking metaharness.
- `github-token`: token used only when `open-pull-request` is true. It is masked
  with the GitHub Actions toolkit when provided and supplied to `git push`
  through Git's askpass credential prompt path, not embedded in the remote URL.

## Outputs

- `run-id`
- `status`
- `final-message`
- `patch-file`
- `ledger-file`
- `handoff-file`
- `pull-request-url`
- `pull-request-number`
- `pull-request-branch`

The action writes outputs before failing the step. If the final result after any
fallback has status `failed` or `cancelled`, the step fails and no pull request
is opened.

## Failure Codes

When setup or input validation fails, the action step failure starts with a
stable `ACTION_*` code before the message. Common examples include
`ACTION_PROVIDER_MISSING`, `ACTION_PROVIDER_UNSUPPORTED`,
`ACTION_TASK_FILE_NOT_FOUND`, `ACTION_CONFIG_NOT_FOUND`,
`ACTION_CONFIG_IMPORT_ERROR`, `ACTION_POLICY_NOT_FOUND`,
`ACTION_POLICY_INVALID`, `ACTION_PULL_REQUEST_TARGET_UNSAFE`,
`ACTION_PULL_REQUEST_DIFF_ERROR`, and `ACTION_GIT_ERROR`.

When a provider run finishes with `failed` or `cancelled`, the action still
writes outputs first, then fails with `ACTION_RUN_FAILED`. Use the `run-id`,
`status`, `ledger-file`, `handoff-file`, and `patch-file` outputs to inspect the
recorded artifacts.

For the full action, SDK, CLI, provider, telemetry, and policy diagnostic
catalog, see [Error codes](error-codes.md).

## Safe Usage

Workflows generated by `hk init --ci github` call `pnpm exec hk`, so the target
repository must include `@metaharness/cli` as a dependency or dev dependency.
The CLI package includes the metaharness adapter packages. Install only the
provider SDK optional peers the workflow will run, for example
`@openai/codex-sdk` for Codex.

Prefer the generated CLI workflow for provider-backed runs. It resolves optional
provider SDK peers from the checked-out workspace where `pnpm install` ran. A
pinned JavaScript action reference such as
`uses: your-org/metaharness/packages/github-action@v0` runs from the action
checkout; mock runs work without real provider peers, but real provider peers
must be resolvable from the action distribution itself. Installing SDK peers only
in the target repository does not satisfy an external pinned action's peer
resolution.

Do not run provider-backed agent workflows on `pull_request_target` by default.
That event can combine untrusted pull request content with elevated repository
permissions and secrets. The action refuses to run on `pull_request_target`
unless `allow-pull-request-target: true` is set.

Prefer least-privilege job permissions. Start with `contents: read`, and grant
`contents: write` plus `pull-requests: write` only to workflows that explicitly
enable `open-pull-request`.

When `open-pull-request` is true, the action commits only staged workspace
changes outside `.harness`; run artifacts remain available through outputs and
artifact upload, not the generated branch. If there are no commit-ready changes,
the action warns and leaves the PR outputs empty.

Do not interpolate issue or pull request text into shell commands. Pass
untrusted text as the action `task` input or a file. metaharness verification
commands are parsed as argv arrays, but workflow `run:` blocks are still shell
scripts and need normal GitHub Actions hardening.

Never echo provider API keys or GitHub tokens. Pass provider credentials through
`env`, and keep raw provider event capture disabled unless you are debugging in a
trusted workflow.

Avoid broad prompts sourced directly from untrusted users. The action does not
log task text, but providers may receive the prompt. Treat issue and PR text as
untrusted instructions and constrain the task with an explicit policy file.

Upload `.harness/runs` with `actions/upload-artifact` if you want to preserve the
ledger, diff, handoff prompt, and verification log after the job finishes. Put
the upload step behind `if: always()` so artifacts are preserved even when the
metaharness step fails with `ACTION_RUN_FAILED`.
